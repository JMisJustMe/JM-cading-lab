# JM Estate Agent Defaults

## Estate production inheritance — ALL PRODUCT BODIES

Before materially building, rebuilding or upgrading an Estate product body, read:

`JM_ESTATE/GOVERNANCE/JM_ESTATE_PRODUCTION_INHERITANCE_STANDARD_v1.0.md`

This is an **Estate-wide** law, not a future-game-only rule.

Canonical inheritance spine:

**RECOVER / AUTHORITY → WORKING BODY → INPUT + FIT → AUTHORED IDENTITY → CONSEQUENCE → VISIBLE FEEDBACK → DEPTH → QUALITY / COMPOSITION → ESTATE CONFORMANCE → REAL-CONTEXT PROOF → CLEAN PROMOTION → ESTATE MOUNT / DELIVERY → OWNER CONTACT → DONATE THE LEARNING**

Rules:
- Apply the law to relevant **old and new** Estate bodies.
- Do not restart an older body merely because stronger Estate organs were proved after it was born.
- Recover the current authoritative body, locate its truthful production rung, and bring it forward from there.
- Preserve frozen parents/ancestors; upgrades move forward through descendants.
- Donor mechanisms may raise a receiving body's starting floor, but donor proof does not replace receiver contact/proof.
- Inherit production intelligence, quality floors and proof discipline — **not another body's identity, theme, genre or furniture**.
- Prefer full-complete production jumps over cosmetic version churn.
- **BUILD ONCE → LEARN ONCE → DONATE MECHANISM → EVERY RELEVANT BODY CAN START / CONTINUE HIGHER.**

## Delivery default — LIVE DIRECT DOOR FIRST

For every JM estate-hosted HTML/web build, the normal owner-facing delivery route is the proved **live direct URL**.

Canonical sequence:

**SOURCE → OPEN_FIRST → ESTATE MOUNT → LIVE PROOF → DIRECT DOOR**

Rules:
- Recover the existing estate/body before rebuilding.
- Preserve one singular canonical `OPEN_FIRST` / front door.
- Mount through the existing JM estate publication rail when available.
- Prove the live URL and required assets before presenting it as live.
- Hand Theodore/JM the live direct link first, every time.
- Sandbox links, ZIPs, duplicate launchers and loose-file bundles are fallback/archive/offline-transfer routes only when a truthful live estate route cannot be produced.
- Live HTTP contact is not the same as owner-side Cold Ding.
- Apply this delivery default to all applicable old and new Estate-hosted HTML/web bodies unless Theodore explicitly overrides it.

## Game production profile — PUKA-PROVED STANDARD BUILD ORDER

For **all JM Estate game work, old and new**, read and follow `games-beyond/JM_GAME_STANDARD_BUILD_ORDER.md` before building or materially upgrading a game.

Canonical production route:

**RECOVER / AUTHORITY → CORE PLAYABLE BODY → CONTROL + FIT → PRIMARY VISUAL BODY → PRESENTATION-ROUTE IDENTITY → WORLD / PROGRESSION CONSEQUENCE → MATERIAL / ENVIRONMENT → COMPOSITION / THEATRE → LIVING VISIBLE-STATE FEEDBACK → ESTATE CONFORMANCE → PRODUCT DEPTH → CURRENT VISUAL-CROWN / DEEP-HOUSE CONVERGENCE → REAL-CONTEXT PROOF → CLEAN PROMOTION → ESTATE MOUNT / LIVE CONTACT → OWNER CONTACT / COLD DING → DONATE THE LEARNING**

Rules:
- PUKA is the proved reference lineage for the order; it is not the identity/template/furniture of other games.
- Reuse the machinery and organs, not poker-specific features or visual identity.
- Older games are not exempt: locate their current rung and bring them forward without restarting already-proved foundations.
- Existing Estate donors may let a game begin or resume higher, but they do not allow the corresponding proof gates to be skipped.
- Protect the playfield before setup chrome.
- Presentation may express authoritative/visible state; it must not become a second hidden game authority.
- Audit mature visual stages against the **current** Estate visual authority, not a remembered older standard.

## Apps + tools production profile

Apps and tools inherit the Estate production law through an app/tool interpretation:

**RECOVER / AUTHORITY → CORE WORKING WORKFLOW → INPUT + DEVICE FIT → AUTHORED INTERFACE IDENTITY → WORKFLOW / STATE CONSEQUENCE → VISIBLE FEEDBACK → INFORMATION / INTERACTION COMPOSITION → PRODUCT DEPTH + RECOVERY → ESTATE CONFORMANCE → REAL DEVICE / BROWSER / FILE-LIFECYCLE PROOF → CLEAN PROMOTION → DELIVERY / MOUNT → OWNER CONTACT → DONATE THE LEARNING**

Rules:
- Do not make tools game-like merely to claim conformance.
- Translate game-specific organs semantically: progression becomes workflow/state consequence; theatre becomes information/interaction composition; playable depth becomes useful workflow/product depth.
- Loading, saving, processing, selection, success, failure, recovery and other state changes should have clear visible consequence where applicable.
- Real-context proof means the actual target device/browser/files/inputs/lifecycle, not source inspection alone.
- Existing apps/tools should be brought forward from their current authoritative state rather than restarted.

## Quality floor

A build is not complete merely because it functions. Preserve the Estate's visual quality standard, responsive fit, source lineage, proof receipts, recoverability, real-context proof, and owner-side acceptance boundary.

**NO ESTATE BODY SHOULD HAVE TO RE-LIVE SOLVED IMMATURITY.**
