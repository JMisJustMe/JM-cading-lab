# JM ESTATE CANONICAL DOOR CONTINUITY STANDARD v1.0

**Status:** ESTATE DEFAULT WEB-CONTINUITY LAW  
**Scope:** All living JM Estate web/HTML/PWA bodies and descendants where a stable public route is technically available.  
**Reference contact:** PUKA demonstrated the practical value of a stable Estate door by allowing the same living web body to reopen against its existing browser-side persisted state rather than being treated as a fresh unrelated carrier.  
**Keeper:** **BODY EVOLVES -> DOOR STAYS -> STATE RETURNS.**

## Core law

A living JM web body should preserve **one canonical public door across descendants whenever technically possible**.

The public door is part of the body's identity and continuity boundary, not merely a delivery address.

The normal delivery sequence remains:

**SOURCE -> OPEN_FIRST -> ESTATE MOUNT -> LIVE PROOF -> DIRECT DOOR**

But once the canonical public door is established, development should normally happen **behind that door** rather than by replacing it with a new owner-facing URL for every descendant.

**ONE LIVING BODY -> ONE CANONICAL DOOR -> MANY LAWFUL DESCENDANTS.**

---

# Continuity obligations

When a JM web body evolves, preserve where applicable:

- the canonical owner-facing URL;
- bookmarks and learned owner habits;
- installed/PWA launch routes and manifest continuity;
- same-origin storage continuity;
- stable storage keys or explicit schema migration;
- service-worker/cache upgrade continuity;
- recoverable application state;
- deep-link or route compatibility where those routes are already public;
- a truthful migration/redirect route if the canonical door genuinely must change.

A version number belongs to the body's lineage and receipts; it should not automatically become a new public door.

**THE DOOR IDENTIFIES THE LIVING BODY, NOT ONE PARTICULAR BUILD.**

---

# State continuity is a mechanism, not URL magic

Preserving the same public door strongly supports continuity, but the URL itself does not store application state.

Browser-side continuity can also depend on:

- origin/host/protocol continuity;
- storage mechanism availability;
- storage-key stability;
- data-schema compatibility and migration;
- browser privacy/site-data rules;
- service-worker/cache behaviour;
- whether the owner has cleared site data or changed browsing context.

Therefore:

**SAME DOOR ENABLES CONTINUITY; PERSISTENCE MECHANISMS EARN THE STATE-RETURN CLAIM.**

Do not claim guaranteed state return merely because the URL remained stable. Prove the actual persistence/re-entry path in the receiving body and target context.

---

# Existing-body rule

For an already-public JM web body:

1. recover the current authoritative source and canonical public door;
2. treat that door as the default continuity boundary;
3. upgrade the source/body behind the existing door;
4. preserve or migrate storage/state deliberately;
5. preserve public routes or provide redirects where necessary;
6. run live route and required-asset proof;
7. run real re-entry/state proof where persistence is part of the body;
8. return the same canonical direct door to the owner unless a documented exception applies.

**DO NOT CREATE A NEW PUBLIC DOOR MERELY BECAUSE THE BODY HAS A NEW VERSION.**

---

# New-body rule

For a new JM web body:

- establish one intended canonical Estate route early;
- keep `OPEN_FIRST` aligned with that public body identity;
- design persistence, PWA and routing around the canonical body rather than temporary carriers;
- use preview, branch, sandbox or file routes only as non-canonical proof/work surfaces;
- promote the proved Estate route as the singular owner-facing direct door.

---

# Door-change exception

A canonical door may change when there is a real technical, security, ownership, architecture or product reason.

A changed door requires an explicit continuity plan. Where technically possible it should include:

- the reason for the change;
- the new canonical door;
- redirect/forwarding from the old door;
- bookmark/deep-link handling;
- PWA/install route handling;
- state/storage migration strategy;
- explicit acknowledgement of anything that cannot migrate automatically, especially across origins;
- proof of the new live route before owner handoff.

**CHANGED DOOR -> EXPLICIT REASON -> CONTINUITY/MIGRATION ROUTE.**

Cross-origin browser storage generally cannot simply be read by a new origin. If a host/origin must change, do not imply automatic state continuity unless an actual migration mechanism proves it.

---

# Delivery hierarchy

For applicable Estate-hosted web bodies, owner-facing delivery priority is:

**CANONICAL PROVED LIVE DIRECT DOOR FIRST.**

Sandbox links, ZIPs, duplicate launchers, loose-file links and temporary preview URLs remain fallback, archive, transfer or proof surfaces. They do not replace the canonical public body while a truthful Estate route exists.

Live HTTP contact remains distinct from owner-side Cold Ding or aesthetic acceptance.

**NO LIVE PROOF -> NO LIVE CLAIM.**  
**NO OWNER CONTACT -> NO OWNER-CONTACT CLAIM.**

---

# Estate inheritance consequence

Canonical-door continuity is an Estate production mechanism and therefore participates in the production-inheritance law:

**BUILD ONCE -> LEARN ONCE -> DONATE MECHANISM -> EVERY RELEVANT BODY CAN START / CONTINUE HIGHER.**

Future and existing web bodies should inherit this continuity floor without inheriting another body's identity, theme or implementation-specific furniture.

Where a product family has stronger continuity requirements, its family-specific standard may strengthen this law but must not silently weaken the canonical-door principle.

**RECOVER THE BODY. PRESERVE THE DOOR. MIGRATE THE STATE. PROVE THE RETURN. CONTINUE.**
