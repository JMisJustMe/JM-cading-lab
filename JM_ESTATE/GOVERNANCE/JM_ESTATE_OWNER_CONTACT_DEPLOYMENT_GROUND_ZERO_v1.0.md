# JM ESTATE — OWNER CONTACT & ON-DEMAND DEPLOYMENT GROUND ZERO v1.0

Status: CANONICAL ESTATE-WIDE OPERATIONAL DEFAULT

## Keeper

**OWNER CONTACT OUTRANKS ASSUMED CONTACT.**

Deep keeper:

**IF JM ASKS FOR THE LINK, THE JOB IS NOT TO REMEMBER A URL. THE JOB IS TO PRODUCE A CURRENTLY REACHABLE DOOR.**

## Scope

This standard applies to every relevant JM Estate web-hosted game, app, tool, site, interface and other owner-facing live body, old and new.

It applies whenever JM asks for a live link, asks to open/use/test a body, says a link is broken, asks for deployment/redeployment, or otherwise makes current owner contact the active goal.

It governs future work and also governs continuation of older work when an earlier chat/body is reopened. It does not rewrite historical chat transcripts; it supersedes weaker delivery practice at the continuation point.

## Ground-zero route

**RECOVER AUTHORITY → IDENTIFY CANONICAL DOOR → CHECK CURRENT CONTACT → REPAIR / REDEPLOY WHEN NEEDED → PROVE LIVE ROUTE → HAND OWNER THE LIVE DOOR → OWNER CONTACT / COLD DING**

If the canonical carrier cannot be restored quickly and a governed recovery carrier exists:

**CANONICAL DOOR FAILS → KEEP CANONICAL IDENTITY → ACTIVATE PROVED RECOVERY CARRIER → OWNER CONTACT → REPAIR PRIMARY DOOR WITHOUT PRETENDING THE RECOVERY CARRIER BECAME A NEW IDENTITY**

## Default operational rules

- A remembered URL, prior receipt, successful source test, CI pass, deployment log or server-side HTTP probe is not enough to claim current owner contact.
- When JM asks for a live link, perform a current contact check when tooling permits before presenting it as working.
- When JM reports `doesn't work`, `ERR_FAILED`, a dead route, stale route or equivalent owner-side failure, treat that report as a real failed contact event. Do not argue with it using an earlier automated PASS.
- If a connected deployment/redeployment rail is available in the current chat, actually use it on command when deployment is necessary. Do not merely explain that deployment could be done.
- Prefer repairing/redeploying the existing canonical door. Do not mint a new canonical public identity merely because the current carrier failed.
- A governed recovery carrier may be activated for immediate owner access while the primary canonical carrier is repaired. The recovery carrier remains recovery custody unless an explicit migration decision changes authority.
- Do not ask JM to clear cache, change browser or perform user-side troubleshooting as the first response to a dead owner door when the host/deployment route has not yet been re-proved.
- Do not call Cold Ding, Crown, final owner acceptance or equivalent until owner-side contact is actually evidenced.
- If the current chat lacks the required connector/tool authority to deploy, state that boundary plainly. Never simulate a deployment claim.
- Delivery actions should happen in the current turn whenever the connected rail allows it; do not promise background work.

## Evidence authority order

For the question **"does the owner have the live body?"**, use this order:

1. **OWNER-SIDE CONTACT / OWNER EVIDENCE**
2. Current external live-route proof from an independent carrier/probe
3. Successful deployment completion
4. Browser/runtime proof against the deployed target
5. CI/source proof
6. Source existence
7. Historical receipt or remembered URL

Higher evidence can invalidate a lower-level assumption. In particular, an owner-side failure overrides an earlier automated live-contact PASS for the purpose of claiming present owner access.

## Link delivery default

When a live body is requested, hand JM the shortest truthful live front door first.

Do not lead with deep implementation files such as `00_OPEN_FIRST.html` when a stable root/index door exists.

Keep technical, sandbox, repository and archive links secondary unless the live direct door is unavailable or JM specifically asks for them.

## PUKA founding proof of this rule

PUKA v0.17A established the concrete operational lesson on 5 September 2026:

- Cloudflare-side automation had reported PUKA reachable.
- Owner physical contact produced `ERR_FAILED`.
- The owner failure was treated as authoritative evidence that the current delivery claim was incomplete.
- A dedicated GitHub Pages owner-recovery deployment rail was invoked from chat.
- The recovery deployment completed successfully.
- JM then opened PUKA successfully on the owner Android device.

This proves the difference between **HOST SAYS LIVE** and **OWNER HAS CONTACT** and establishes the Estate-wide default above.
