# JM ESTATE PRODUCTION INHERITANCE STANDARD v1.0

**Status:** ESTATE DEFAULT PRODUCTION-INHERITANCE LAW  
**Scope:** ALL JM Estate product bodies — old and new games, apps, tools, engines, studios and other executable/interactive bodies where the stages are applicable.  
**Reference proof lineage:** PUKA exposed the first proved full game-production ladder; the Estate inherits the production intelligence, not PUKA's identity.  
**Keeper:** **NO ESTATE BODY SHOULD HAVE TO RE-LIVE SOLVED IMMATURITY.**

## Core law

When one Estate body proves a stronger production mechanism, quality floor, proof gate or delivery route, that learning becomes available to every relevant Estate body.

**BUILD ONCE -> LEARN ONCE -> DONATE MECHANISM -> EVERY RELEVANT BODY CAN START / CONTINUE HIGHER.**

This law is **retroactive-forward**:

- it applies to bodies created before this standard existed;
- it applies to bodies created after this standard exists;
- it does not rewrite frozen ancestors;
- it does not require an old body to restart from rung 0;
- it does not allow an inherited organ to skip proof in the receiving body;
- it carries production intelligence, not another body's theme, furniture, genre or identity.

**STEAL THE MACHINERY, NOT THE FURNITURE.**  
**MESH != MERGE.**  
**RECOVER BEFORE REBUILD.**  
**CONTACT BEFORE CROWN.**

---

# Estate production spine

Every product family adapts this spine to its own body:

**RECOVER / AUTHORITY -> WORKING BODY -> INPUT + FIT -> AUTHORED IDENTITY -> CONSEQUENCE -> VISIBLE FEEDBACK -> DEPTH -> QUALITY / COMPOSITION -> ESTATE CONFORMANCE -> REAL-CONTEXT PROOF -> CLEAN PROMOTION -> ESTATE MOUNT / DELIVERY -> OWNER CONTACT -> DONATE THE LEARNING**

The stages are semantic obligations, not literal UI furniture.

A family may combine adjacent stages when its current body and donors already satisfy them, but the receiving body must still prove the relevant gates.

---

# Existing-body rule — LOCATE, DO NOT RESTART

For an existing Estate body:

1. recover the strongest current authoritative body and its lineage;
2. identify what it already proves;
3. locate the first materially missing or obsolete production stage;
4. identify newer Estate organs/standards that can lawfully donate forward;
5. preserve frozen parents and source identity;
6. upgrade from the body's current state rather than recreating its childhood;
7. run the missing proof gates in the receiving body's real context;
8. promote a clean descendant only after proof;
9. donate any new learning back to the Estate.

**OLD BODY != EXEMPT BODY.**  
**OLDER BIRTH DATE != LOWER PERMANENT QUALITY CEILING.**

No body is required to repeat already-solved immaturity merely because the solution was discovered later.

---

# New-body rule — START AS HIGH AS EVIDENCE ALLOWS

For a new Estate body:

- recover current Estate organs before inventing replacements;
- begin at the highest lawful production floor supported by those donors;
- preserve the new body's own identity and sovereign mechanism;
- prove inherited organs in the new context;
- do not use version churn as a substitute for meaningful production jumps.

**FULL BODY -> STRAIGHT RUN -> CORRECT AFTER.**

# Family profiles

## Games

All JM Estate games — **old and new** — follow the detailed game profile in:

`games-beyond/JM_GAME_STANDARD_BUILD_ORDER.md`

PUKA is the proved reference lineage for that game's production order. It is not the template, theme or furniture of other games.

The game profile includes playable-body authority, controls/fit, authored visual objects, presentation routes, world/progression consequence, material/environment quality, composition/theatre, visible-state feedback, Estate conformance, product depth, current visual-crown convergence, real-context proof, clean promotion, Estate mount, owner contact and donation.

## Apps and tools

Apps and tools inherit the same production intelligence through an app/tool interpretation rather than literal game stages:

**RECOVER / AUTHORITY -> CORE WORKING WORKFLOW -> INPUT + DEVICE FIT -> AUTHORED INTERFACE IDENTITY -> WORKFLOW / STATE CONSEQUENCE -> VISIBLE FEEDBACK -> INFORMATION / INTERACTION COMPOSITION -> PRODUCT DEPTH + RECOVERY -> ESTATE CONFORMANCE -> REAL DEVICE / BROWSER / FILE-LIFECYCLE PROOF -> CLEAN PROMOTION -> DELIVERY / MOUNT -> OWNER CONTACT -> DONATE THE LEARNING**

Examples of translation:

- game `core playable body` -> app/tool **core working workflow**;
- game `world / progression consequence` -> **workflow/state consequence**;
- game `composition / theatre` -> **information hierarchy + interaction composition**;
- game `product depth` -> **real workflow depth, persistence, recovery, re-entry, interoperability and useful breadth**;
- game `living visible-state feedback` -> **clear visible consequence for loading, saving, selection, processing, success, failure, recovery and state change**;
- game `real-context proof` -> **actual target browser/device/file/input/lifecycle proof**, not source inspection alone.

A tool must not become game-like merely to comply. It inherits the maturity route, not game furniture.

## Engines, studios and creator bodies

Engines/studios inherit the same spine with emphasis on:

- recoverable authority and donor lineage;
- a working creation/runtime loop;
- control/input fit;
- legible authored workspace identity;
- visible consequence of edits/actions;
- recovery, trace and state integrity;
- meaningful production depth;
- real-context build/runtime proof;
- clean promotion and reusable donation.

---

# Proof cannot be inherited by name

Inheritance can raise the starting floor, but a donor's proof does not automatically become the recipient's proof.

Examples:

- a responsive organ proven in one game must still be contacted in the receiving game;
- a persistence mechanism proven in one app must still be tested against the receiving app's state;
- a visual grammar may be donated without copying palette, theme or composition;
- an Estate conformance suite may be reused, but the new body must actually pass it.

**DONOR PROOF ENABLES A HIGHER START; RECEIVER CONTACT EARNS THE RECEIVER CLAIM.**

---

# Crown and version boundary

Prefer **full-complete production jumps** over cosmetic version churn.

Do not crown a body because it inherited a mature organ. Crown only what the receiving body has actually contacted and proved.

Owner physical/aesthetic acceptance remains separate where applicable.

**NO DING, NO CLAIM.**

---

# Governance consequence

From this standard forward:

- all old and new games are in scope;
- apps/tools are in scope through the appropriate family translation;
- future Estate product families should define their own profile only where the shared spine requires interpretation;
- a family-specific profile may strengthen or specialise this law but must not silently narrow away the Estate-wide inheritance principle;
- frozen ancestors remain preserved; upgrades move forward through descendants;
- current Estate standards should be recovered at the time of material upgrade rather than relying on an older remembered quality floor.

**DO NOT RESTART THE BODY. LOCATE IT ON THE CURRENT LADDER AND BRING IT FORWARD.**
