# JM Inline Contact — Maximisation Roadmap v0.2

This roadmap assumes the Third Ding proof is frozen and preserved. The job now is not to keep proving that Inline Contact can exist; it is to make the route useful, repeatable, diagnosable, and expandable.

## Priority 0 — preserve the win

- Keep v0.1.2 immutable as known-good rollback.
- Retain the original laptop and phone recordings plus decisive stills in Zionfolder.
- Keep proof claims literal: deliberate inline contact is proved; universal client behavior is not.

## Priority 1 — convert the probe into a dependable host instrument

1. Add a lightweight capability/status surface so ChatGPT and humans can tell what the server exposes without invoking a game body.
2. Add host lifecycle hardening for repaint/recovery events observed on phone: `visibilitychange`, `pageshow`, focus, resize/orientation and first-frame repaint.
3. Preserve local contact state across harmless redraws within the widget lifetime.
4. Emit a visible runtime/build identifier in the UI so screenshots and videos identify the exact body.
5. Keep the public probe non-sensitive and read-only.

## Priority 2 — first real playable descendant

Mount a real existing JM playable body through the proven adapter. Do not create a new engine.

Preferred donor chain:

`JM GameCore / existing game body -> playable IR / OneBody -> JM Visual Interaction Runtime -> ChatGPT Host Adapter`

Acceptance:

- body appears in-chat;
- primary control works by touch/pointer;
- state visibly changes;
- at least one meaningful game loop exists;
- no external-file opening is required;
- the body can be named/formalised after contact rather than before it.

## Priority 3 — make invocation natural

Target user grammar:

- `@JM Inline Contact make me a game`
- `@JM Inline Contact inline-probe this`
- `@JM Inline Contact play this here`
- `@JM Inline Contact resume the current body`

The adapter should route these intents onto existing JM bodies/presets rather than inventing a parallel authoring system.

## Priority 4 — reliability matrix

Track separately:

- ChatGPT web desktop
- ChatGPT Android app
- ChatGPT mobile web
- iOS when available for test

For each surface record:

- resource rendered;
- first paint latency;
- pointer/touch accepted;
- state updated;
- repaint after background/foreground;
- conversation reload recovery;
- whether app attachment remains selected;
- whether tool invocation is allowed in that conversation type.

## Priority 5 — observability without surveillance

Add only non-sensitive operational receipts:

- adapter version;
- body id/version;
- resource uri;
- tool invoked;
- server render receipt;
- host-proof flag remains false until user-side contact evidence exists.

Do not collect names, private content, precise location, or persistent gameplay history merely for diagnostics.

## Priority 6 — submission/public route

- Preserve safe public MCP endpoint.
- Use the frozen Third Ding recordings to prepare the required demo recording.
- Complete plugin/app metadata truthfully.
- Keep commerce disabled unless a real future physical-goods use case exists.
- Do not publish private/frozen donor bytes through the public probe.

## Priority 7 — maximise the new contact route

Once a first real playable descendant is stable, treat Inline Contact as a host target available to other JM bodies:

- games;
- visual interaction experiments;
- inspectors/debuggers;
- small creative instruments;
- training/play surfaces;
- TraceBox/receipt viewers;
- body selectors/launchers.

The governing rule remains: **host adapter, not replacement platform**.

## Definition of maximised enough for v0.2

v0.2 is ready to graduate from managed beta when:

- one non-probe JM playable body is repeatably playable in-chat;
- desktop and one mobile route pass the contact matrix;
- host repaint recovery is tested;
- invocation language is simple enough for a non-developer;
- rollback to v0.1.2 is documented and tested;
- the submission/demo package is complete;
- no source identity, donor privacy, or Ding criteria have been weakened.
