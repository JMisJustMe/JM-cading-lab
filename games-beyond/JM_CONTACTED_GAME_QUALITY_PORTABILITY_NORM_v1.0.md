---

## Why this exists

KICSHIFT proved a new practical floor: a visually embodied, mobile-playable game can be forged quickly on an external surface, preserved as ordinary source, separated from that forge, rebuilt independently, mounted behind the Estate's canonical public door, mirrored to another carrier, and physically played by the owner without losing the game body.

That is useful Estate learning. It should not remain trapped inside KICSHIFT.

It also should **not** become a mandate that every game must become an arena fighter, a 3D body, a React project, a Three.js project, or a heavier application.

The Estate therefore promotes the **qualities and proof route** as a default reference norm only where they are relevant and comparatively beneficial.

---

# Core law

A receiving game should inherit a KICSHIFT-proved quality when all four questions are sufficiently satisfied:

1. **CONTACT BENEFIT** — does it materially improve feel, clarity, embodiment, responsiveness, accessibility, spectacle, usefulness or player understanding?
2. **CONTINUITY BENEFIT** — does it materially improve source independence, recoverability, lineage, portability, canonical-door continuity or release safety?
3. **IDENTITY FIT** — does it strengthen or preserve the receiving game's own identity rather than turning it into KICSHIFT-shaped furniture?
4. **COST TEST** — is the benefit worth the added code, assets, runtime weight, maintenance burden, complexity and proof surface?

If the answer is no, the body stays smaller.

**MORE CAPABILITY IS NOT AUTOMATICALLY MORE QUALITY.**  
**COMPARATIVE BENEFIT DECIDES INHERITANCE.**

## PUKA Lite — prototype / small-body floor

Use for rapid playable truth, lightweight comparison, early contact and the smallest relevant implementation.

PUKA Lite remains valid. KICSHIFT does not erase it.

## PUKA Super / production ladder — mature production-order floor

Use the established Estate build order to recover, compose, prove, deepen and promote a game without restarting it.

The PUKA ladder remains the default production sequence and maturity locator.

## KICSHIFT FLAZ — contacted richer-game quality + portability reference

Use as the reference when a game benefits from a higher embodiment/contact/portability floor, especially for richer action, embodied, real-time, visually spatial, web-delivered or 2.5D/3D games.

It may also donate mechanisms to simpler games when those mechanisms provide a clear comparative benefit without bloating the receiver.

**PUKA TELLS US HOW TO BUILD FORWARD. KICSHIFT NOW SHOWS HOW HIGH A RELEVANT CONTACTED BODY CAN START AND STILL REMAIN PORTABLE.**

# Default KICSHIFT-proved qualities

The following are now preferred defaults **when relevant**:

### 1. Source body separate from forge

The game must be recoverable as ordinary source/body outside the surface that helped create it.

External forge != sovereign home.

### 2. Independent build route

A release-worthy body should have a known way to install/build outside its authoring forge when its format permits that distinction.

### 3. Carrier independence

For public web games of sufficient relevance, one host should not be allowed to become the game's identity or only survival route.

Prefer:

`JM SOURCE AUTHORITY → BUILD → REPLACEABLE CARRIER(S) → CANONICAL PUBLIC DOOR`

### 4. Canonical-door continuity

Preserve one stable owner/public route whenever technically possible. Move carriers beneath the door rather than casually changing the game's identity boundary.

### 5. Real-device contact before mature crown

Emulation and browser QA are useful but do not impersonate owner physical-device contact.

### 6. Stronger embodiment where it pays

Characters, play objects, worlds, effects, lighting, depth and visible consequence should rise above placeholder presentation when the game's value benefits from it.

A real circle with useful depth may beat fake dimensional clutter; a flat body may beat 3D when flatness is the better game.

### 7. Controls belong to the playfield

Inputs should be placed and shaped around actual action, aim, movement and visibility. HUD/control chrome must not unnecessarily obstruct the field.

### 8. Perceivable action consequence

Movement, attack, impact, defence, dodge, deflect, transport, charge, release and state changes should produce readable consequence appropriate to the game.

### 9. Lean carrier discipline

Preserve best practical quality, lowest practical size and full intended contact. Shared organs and assets should be reused rather than duplicated.

### 10. Trace + recovery + lineage

A sophisticated body must remain recoverable. Higher visual/game quality does not excuse weaker ancestry, proof or rollback.

# What is NOT inherited automatically

The following are **not** Estate defaults merely because KICSHIFT currently uses them:

- arena combat;
- this control layout;
- KIC / Dash / Guard / Shift naming;
- Three.js;
- React;
- React Three Fiber;
- TypeScript;
- Vite;
- Tailwind;
- 3D;
- landscape orientation;
- this visual palette;
- this HUD composition;
- Lovable or any other particular forge.

These remain replaceable implementation/furniture choices.

**THE LAW IS THE CAPABILITY + CONTACT + CONTINUITY. THE FRAMEWORK IS A CURRENT CARRIER.**

# Progressive JM-native rewiring law

A proven conventional/open-source implementation may be progressively rewired into JM-native bodies when there is a real reason to do so.

Do not destroy the contacted parent first.

Default route:

`FLAZ PARENT → CLEAN DESCENDANT → REPLACE / ADAPT ONE ORGAN → BUILD → CONTACT → COMPARE → KEEP OR ROLLBACK → NEXT ORGAN`

Candidate JM-native replacements can include:

- input/contact routing;
- movement and aiming;
- combat/interaction mechanics;
- state authority;
- deterministic simulation;
- trace and recovery;
- character embodiment;
- camera/control truth;
- scene composition;
- packaging and deployment;
- eventually renderer/runtime layers where replacement produces actual benefit.

**JM-NATIVE IS NOT A FREE PASS. A REWIRE MUST EARN ITS PLACE THROUGH CONTACT.**

---

# Relevant-game release floor

For games where portability/release continuity materially matters, prefer this full route before FLAZ or production crown:

`AUTHOR / FORGE → SOURCE COPY → JM AUTHORITY → INDEPENDENT BUILD → RUNTIME CONTACT → MOBILE / OWNER DEVICE CONTACT → PUBLIC DOOR → ALTERNATE CARRIER OR RECOVERY ROUTE → RECEIPT → FLAZ`

A tiny local experiment need not satisfy every public-carrier gate. A serious publicly released Estate game should satisfy more of them.

Scope should be proportional to consequence.

# Comparative-benefit examples

### A lightweight card/puzzle game

May inherit source independence, canonical-door continuity, mobile proof and lean packaging while remaining visually flat and tiny.

### A real-time shooter/sports/drift game

May additionally inherit richer embodiment, spatial aim logic, layered controls, camera truth, visible contact feedback and 2.5D/3D depth.

### An old HTML game

Should not restart. Recover its strongest current body, locate its weak rung, then inherit only the modern mechanisms that materially raise it.

### A new high-value game

May begin much higher because PUKA + KICSHIFT + other Estate donors have already earned a higher starting floor.

# Promotion rule

A KICSHIFT-like quality jump becomes an Estate default only after contact proves it outside the source body's local context.

KICSHIFT v0.1 now qualifies as the first reference specimen because it proved:

- source separation from its original forge;
- independent build;
- independent WebGL execution;
- mobile touch execution;
- canonical Estate public contact;
- second-carrier contact;
- public byte parity;
- physical owner-phone run completion;
- positive owner acceptance;
- FLAZ closure.

This is enough to donate the route and quality expectations — not its identity.
