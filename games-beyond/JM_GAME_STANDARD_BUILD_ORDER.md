# JM GAME STANDARD BUILD ORDER — PUKA-Proved Production Ladder v1.0

**Status:** ESTATE DEFAULT GAME-BUILD ORDER  
**Scope:** JM Games&Beyond game bodies and descendants unless Theodore/JM explicitly overrides the order for a specific body.  
**Reference proof lineage:** PUKA through v0.13A Deep House Visual Convergence.  
**Keeper:** **BUILD THE BODY. PROTECT THE PLAYFIELD. DEEPEN THE WORLD. PROVE THE CONTACT. DONATE WHAT WAS LEARNED.**

## Why this exists

PUKA demonstrated that a game can start later than older Estate games and still overtake them in professional/polished appearance when the build order carries forward what earlier bodies already learned.

This document turns that proved route into the Estate default. It does **not** make PUKA the identity, theme, mechanics or visual furniture of future games. Future games inherit the **order, organs, quality floor and proof discipline** only.

**STEAL THE MACHINERY, NOT THE FURNITURE.**  
**MESH != MERGE.**  
**BUILD ON THE ESTATE; DO NOT RESTART BENEATH IT.**

---

# Canonical production order

## 0. RECOVER / ORIENT / DECLARE AUTHORITY

Before building:

- recover the strongest current parent/body and donor organs;
- identify the game's sovereign mechanic/state authority;
- identify what is reused, adapted, mounted or newly authored;
- preserve frozen donor identities and lineage;
- define one canonical front door / OPEN_FIRST;
- define the owner-facing live route when the body is estate-hosted.

**Gate:** no rebuild may silently replace a recoverable stronger body.

---

## 1. CORE PLAYABLE BODY

Build the smallest **real game**, not a visual mock-up:

- canonical state;
- rules / win-loss / consequence;
- input route;
- reset / continuation;
- deterministic or bounded randomness where needed;
- basic trace/error boundary;
- playable first loop.

Graphics may be provisional here, but the body must actually play.

**Gate:** mechanics work before decorative complexity is allowed to become authority.

---

## 2. CONTROL + FIT RESET

Before premium art, make the game physically usable:

- Android-first playfield;
- portrait/landscape routes where relevant;
- zero accidental horizontal overflow;
- safe-area handling;
- visible primary actions;
- 44px minimum touch-contact floor unless a stronger applicable standard exists;
- no setup/profile chrome dominating gameplay;
- desktop/laptop route remains usable without requiring mouse-only control.

**Law:** **PROTECT PLAYFIELD BEFORE SETUP CHROME.**

**Gate:** the usable body must fit before visual richness is piled onto it.

---

## 3. PRIMARY VISUAL BODY

Replace placeholder representation with authored game-specific visual objects:

- cards / pieces / creatures / vehicles / avatars / tiles / projectiles / tools as applicable;
- readable hierarchy;
- dimensional form;
- game-specific iconography;
- original assets or lawful donor mechanisms;
- clear active / inactive / hidden / selected states.

Do not rely on one background or generic gradients to carry the whole art direction.

**Gate:** the things the player actually manipulates must deserve attention before environmental ornament does.

---

## 4. PRESENTATION-ROUTE IDENTITY

When the game has multiple modes, orientations, devices, roles or presentation routes:

- give each route a genuine composition;
- keep the shared game state sovereign;
- do not duplicate hidden authority inside presentation code;
- make routes semantically equivalent where they should be, not necessarily pixel-identical;
- preserve distinct identities instead of making one route a stretched fallback of another.

**Gate:** one state may have multiple presentations, but presentation must not become a second engine.

---

## 5. WORLD / PROGRESSION CONSEQUENCE

If the game contains progression, rank, stage, difficulty, faction, arena, room, biome or campaign state, make it visible in the world:

- environment changes;
- material/status escalation;
- room/arena consequence;
- progression cues beyond text/badges;
- new visual/state pressure without erasing the core playfield.

**Law:** progression must become perceivable consequence, not merely a number increasing.

---

## 6. MATERIAL + ENVIRONMENT QUALITY PASS

Now deepen the authored world:

- material language;
- lighting hierarchy;
- depth planes;
- environmental identity;
- shadows / highlights / grain / glass / metal / felt / stone / organic material as appropriate;
- richer background only where it supports meaning and focus.

This is not a licence for ornament soup.

**Gate:** richness must improve identity, focal clarity or state meaning.

---

## 7. COMPOSITION / THEATRE PASS

Turn a stack of UI regions into a deliberate game scene:

- focal hierarchy;
- staging between opponent / field / player / objective;
- runway / arena / lane / board / combat-space structure as applicable;
- seat / zone / HUD architecture;
- readable primary action area;
- stronger first-glance understanding.

**Gate:** the eye should know where play is happening before it reads explanatory text.

---

## 8. LIVING VISIBLE-STATE FEEDBACK

Give visible actions physical/perceivable consequence without creating a second authority:

- chip mass / impact / recoil / trail / pulse / board response / contact wave / state glow as appropriate;
- feedback derived only from already-authoritative or already-visible state;
- bounded motion;
- reduced-motion route;
- no hidden-state leakage.

**Law:** **INTERACTION MUST PRODUCE PERCEIVABLE CONSEQUENCE.**

**Gate:** presentation may express state; it may not invent state.

---

## 9. ESTATE CONFORMANCE PASS

Run the game against independent Estate standards rather than letting the game grade itself:

- real browser/runtime contact;
- separate mobile-touch and desktop contexts;
- exact requested viewport identity;
- zero horizontal overflow;
- touch-contact floor;
- keyboard/focus route where relevant;
- reduced motion;
- safe-area behaviour;
- browser/page-error gate;
- protected playfield floor;
- accessibility boundaries appropriate to the body.

**Gate:** source looking correct is not enough; the rendered body must pass.

---

## 10. PRODUCT-DEPTH PASS

After the game already looks and plays like a proper body, deepen what makes it worth returning to:

- persistence / re-entry;
- history / review / replay / mastery as appropriate;
- teaching / onboarding / progression / unlocks;
- richer AI or opponent behaviour;
- decision depth;
- session continuity;
- recovery from interrupted state;
- content breadth without bloating the main playfield.

This stage is game-specific. Do not force PUKA's teaching/history organs into games that do not need them.

**Gate:** deepen the product, not merely the menu count.

---

## 11. DEEP HOUSE / CURRENT VISUAL-CROWN CONVERGENCE

Before calling a mature visual stage complete, audit against the **current** Estate visual authority rather than an old remembered standard.

Default inherited laws currently include:

- maximal visual depth is a core function;
- depth must carry meaning;
- interaction must produce perceivable consequence;
- shared house does not erase distinct room/game identity;
- protected visual field;
- meaningful D0 -> D1 -> D2 -> D3 depth where applicable;
- recovery remains reachable;
- motion does not substitute for consequence.

Do **not** copy another body's palette/theme merely to claim conformance. Donate the visual grammar, not the identity.

---

## 12. REAL-CONTEXT PROOF + VISUAL EVIDENCE

Before promotion:

- static/source regressions;
- core/game tests;
- real Chromium/browser runtime;
- mobile touch context;
- tablet/laptop/desktop contexts where applicable;
- orientation continuity where applicable;
- persistence/reload contact where applicable;
- viewport-only screenshots;
- zero console/page errors;
- proof artifact/receipt;
- no automated aesthetic-crown claim.

**Law:** real-viewport structural proof != owner aesthetic acceptance.

---

## 13. PROMOTE CLEAN DESCENDANT

Before main/public authority moves:

- compare against current parent/main;
- require zero-behind or reconcile current authority first;
- do not force-promote a stale branch;
- promote the exact proved descendant;
- preserve donor/parent ancestry.

**Gate:** branch success alone is not production contact.

---

## 14. ESTATE MOUNT + LIVE CONTACT + DIRECT DOOR

For estate-hosted HTML/web games use:

**SOURCE -> OPEN_FIRST -> ESTATE MOUNT -> LIVE PROOF -> DIRECT DOOR**

- deploy through the authoritative Estate rail;
- contact the exact production route/assets;
- seal the public-contact receipt;
- keep one stable owner-facing live URL whenever possible;
- give the proved live direct door first.

Sandbox/ZIP/file routes are fallback/archive/offline-transfer routes, not normal owner delivery.

---

## 15. OWNER CONTACT / COLD DING / CROWN BOUNDARY

Owner physical contact remains separate:

- real device feel;
- aesthetic quality;
- controls;
- lifecycle on owner hardware;
- enjoyment / clarity / frustration;
- any physical-device-only behaviour.

Automated proof must never manufacture Cold Ding or aesthetic crown.

**NO DING, NO CLAIM.**

---

## 16. DONATE THE LEARNING

After a successful jump:

- identify reusable mechanisms;
- donate them to the Estate as organs/standards/tests;
- preserve the source game's identity;
- make the next game start higher;
- upgrade the standard if a newer body proves a stronger order.

**BUILD ONCE -> LEARN ONCE -> DONATE MECHANISM -> NEW BODY STARTS HIGHER.**

# Full-complete jump rule

Development should prefer **full-complete jumps** over tiny cosmetic version churn.

A jump may combine several adjacent stages when the body is strong enough, but it must still preserve the corresponding gates. Existing Estate donors may allow a new game to begin above earlier stages; they do not allow proof to be silently skipped.

**FULL BODY -> STRAIGHT RUN -> CORRECT AFTER.**  
**CONTACT BEFORE CROWN.**  
**NO RESTART.**
