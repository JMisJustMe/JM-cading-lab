# JM HUMAN-SCALE INTERACTION STANDARD v1.0

**Status:** ACTIVE ESTATE INTERACTION STANDARD  
**Scope:** executable/interactive JM Estate bodies where ordinary use currently exposes more implementation structure than the user's intention requires.  
**Parent law:** `JM_ESTATE/GOVERNANCE/JM_ESTATE_PRODUCTION_INHERITANCE_STANDARD_v1.0.md`  
**Reference implementation families:** JM Contact Organ, Visual Story Studio production runway, TheoPlus Estate Instrument, KOCODIFY/SELF-RUN.

## Keepers

**THE BODY CARRIES THE COMPLEXITY. THE PERSON CARRIES THE INTENTION.**

**REAL DEPTH DOES NOT REQUIRE PERFORMING DEPTH.**

**SIMPLE DOOR. DEEP HOUSE.**

## Governing route

Ordinary interaction should expose the shortest honest route from human intention to meaningful consequence:

**INTENTION -> SIMPLE CONTACT -> REAL MACHINERY -> CLEAR CONSEQUENCE -> NEXT**

When something fails or the owner asks to inspect it:

**BUG / QUESTION -> WHAT HAPPENED -> RETRY / RECOVER -> DETAILS / TRACE**

Technical stages, identifiers, host data, packet state, thread state, hashes, logs, diagnostic routes and legacy numbered steps remain available where useful. They do not have to be the ordinary front door.

## Dispenser / remote-control rule

A dispenser does not remove its pumps because the user presses one button. A remote does not remove the television's circuitry because the user presses Volume +.

Therefore:

- simplification MUST NOT mean deleting capability;
- technical depth MAY remain fully real underneath;
- the ordinary surface SHOULD express human intentions rather than internal component choreography;
- advanced detail SHOULD be progressively disclosed;
- failure SHOULD surface the smallest useful explanation first, with deeper trace one level below;
- the user SHOULD NOT have to reenact machinery that the body already knows how to perform.

## Estate inheritance

This standard is retroactive-forward.

For an existing body:

1. recover the strongest current authoritative body;
2. preserve frozen parents and provenance;
3. identify the ordinary human intention(s);
4. identify which internal steps the body can already perform itself;
5. compress those steps behind the intention without deleting them;
6. expose clear consequence and recovery;
7. keep diagnostics under Details / Trace;
8. prove the descendant in its actual receiver context;
9. only then promote/crown that receiver scope.

**DO NOT RESTART THE BODY. RECODIFY THE ROUTE.**

## Surface modes

### 1. CALM FRONT
Best for tests, setup, connection, deployment, recovery and other workflows where one intention can legitimately trigger a known sequence.

Default shape:

`READY -> TEST / CONNECT / RUN / RECOVER -> PASS / BUG -> NEXT`

The deep body remains reachable through **DETAILS / TRACE**.

### 2. GUIDED WORK
Best for editors, studios, notebooks, builders and tools that genuinely require several user decisions.

Do not falsely force these into one button. Instead:

- foreground the current productive action;
- group secondary/advanced controls;
- keep state consequence visible;
- keep navigation semantic rather than developer-structural;
- expose the next meaningful action without making the owner hunt through the machinery.

### 3. EXPERT OPEN
For deliberate inspection/debugging. Full machinery may be visible because inspecting machinery is itself the user's intention.

## Test and proof surfaces

Test bodies receive the strongest compression rule.

Ordinary route:

**OPEN -> TEST -> PASS / BUG -> NEXT**

Internal test stages MAY keep stable identities such as `0.5`, `0.6`, packet names or state IDs for traceability. Those identities MUST NOT automatically become the owner's workflow.

On BUG, prefer:

- plain-language stop point;
- Retry;
- Details / Trace;
- exact technical output beneath that.

**A LONG LIST MAY REMAIN THE MACHINE'S QUEUE WITHOUT BECOMING THE PERSON'S JOB.**

## Cross-device semantics

Phone and laptop are separate physical surfaces but may be two roles in one semantic body.

Requirements:

- semantic parity over pixel parity;
- no mouse-only authority where another practical route can exist;
- preserve mobile fit, keyboard/trackpad fit, touch fit and re-entry;
- one device MAY initiate where technically lawful, but the consequence must state which side actually proved what;
- device-specific detail belongs under the shared human intention, not above it.

## Optional support cannot rule the route

A support layer that fails MUST NOT silently gain authority over an otherwise usable essential route unless the support layer is genuinely required for correctness/safety.

**OPTIONAL ROUTES MUST NOT GAIN ESSENTIAL AUTHORITY.**

Where a support feature is unavailable, prefer bounded fallback + visible limitation + trace over total collapse.

## No cosmetic compliance

A body is NOT human-scale merely because:

- buttons are larger;
- labels are shorter;
- a dashboard exists;
- a wrapper says START;
- developer internals were deleted;
- a one-button front exists but merely dumps the user into the old checklist.

Compliance requires the lived route to change meaningfully.

## Receiver proof boundary

Donor proof raises the starting floor but does not grant receiver proof.

Assistant-side source/static/runtime checks may prove the implementation is coherent. They do not replace:

- owner phone contact;
- owner laptop contact;
- real cross-device consequence;
- target file lifecycle;
- target browser/runtime behavior;
- felt/visual acceptance where explicitly required.

**NO DING, NO CLAIM.**

## Propagation law

When this standard is applied to one body, the mechanism becomes available to all relevant siblings.

Do not hand-patch the same interaction pattern forever.

**BUILD ONCE -> LEARN ONCE -> DONATE THE ORGAN -> ADAPT PER BODY -> PROVE PER RECEIVER.**

A body may lawfully receive one of these dispositions:

- `MATERIALIZED_HUMAN_SCALE_DESCENDANT`
- `ALREADY_MEETS_STANDARD_NO_REBUILD`
- `READY_TO_GRAFT_EXACT_SOURCE_REQUIRED`
- `RECOVERY_HOLD_SOURCE_INSUFFICIENT`
- `OWNER_CONTACT_OPEN`

A registry is accounting, not proof. `GOVERNED != WIRED != EXECUTED != CONTACTED` remains binding.
