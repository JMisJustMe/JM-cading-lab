3. The Ecosystem Logic

The ecosystem is not just “lots of projects.”

It has an operating structure:

CENTRAL SWITCHBOARD
→ ROOTRAILS
→ BRANCHES
→ PUBLIC OUTPUT

Core law

The Switchboard routes.
RootRails speed up.
Branches build.
Public Output releases.

Central Switchboard — Routes, indexes, prioritises and prevents overload.
RootRails — Finds shared hidden engines across projects.
Branches — Build the actual products, worlds, tools, games and books.
Public Output — Turns internal source into releaseable bodies.

The ecosystem does not need every chat updated. It needs the correct route.

Do not scatter. Route.
Do not merge everything. Connect by hidden engine.
Do not restart. Continue from active body.

4. RootRails Logic

RootRails prevent repetition without merging identities.

The RootRail algorithm is:

Which projects share the same hidden engine?
What reusable logic can be lifted out?
Which branches benefit if this is built once?
What branch should test it first?
What must not be merged?

First seven RootRails

Playable Systems Rail
Field → Object → Action → Rule → State Change → Feedback → Win/Fail

Forge / World-Making Rail
Word-seed → Zone → Entity → Rule → Artifact → World Record → Output

Trace / Route / Recovery Rail
Input → Route → State → Trace → Recovery → Next Test

Body / Device / Control Rail
Body Need → Grip/Input → Route → Feedback → Comfort → Control → Prototype

Story / Character / Motion Rail
Character → Pressure → Motion → Choice → Consequence → Arc → Episode

Voice / Music / Performance Rail
Source Phrase → Rhythm → Voice → Scene → Track → Performance Output

Public Output Rail
Internal Source → Public Frame → Format → Package → Release Shelf

RootRails do not say: make all projects the same.

They say:

build shared logic once
test it in one branch
reuse it where it belongs
keep branch bodies separate

5. TraceBox / RouteBox Logic

TraceBox is the clearest expression of recoverability logic.

It is not just a note app, tracker, or framework.

It is:

INPUT
→ ROUTE
→ STATE
→ TRACE
→ READBACK
→ RECOVERY
→ NEXT TEST

Normal systems become black boxes:

input goes in
something happens
result appears
route is hidden

TraceBox says:

make the route readable
make the state visible
make the change recoverable

That is why “translucent box” fits better than black box.

TraceBox is proof that logic can be visible, recoverable, exportable, testable and correctable.

It overlaps with the game engine because both need state-change.

Game engine asks: Can the state-change become playable?
TraceBox asks: Can the state-change become readable and recoverable?
Switchboard asks: Can the state-change be routed to the correct branch?
FlowTalk asks: Can the state-change preserve meaning through expression?

Same spine. Different output.
